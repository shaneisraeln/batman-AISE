BATMAN Documentation

Runtime security for machine-learning inference APIs.

BATMAN is a model-agnostic security layer that sits in front of an ML model. It analyzes behavior across inference requests, detects suspicious patterns (API abuse, anomalous inputs, systematic model probing / extraction), and enforces an action with a deterministic policy engine: ALLOW, LOG, RATE_LIMIT, BLOCK, or ESCALATE.

You integrate in one of two ways:

  • Python SDK — a lightweight client (batman-ml) that routes inference through BATMAN.
  • REST / gateway — register your existing model endpoint and let BATMAN proxy to it.
The policy engine is authoritative. The LLM investigation layer explains and recommends, but never overrides an enforcement decision.

Quickstart

From zero to a protected model in five steps.

1. Create an account & get a token

curl -X POST $BATMAN/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"your-strong-password"}'
# -> {"token":"...", "token_type":"bearer"}

2. Create a project

curl -X POST $BATMAN/projects \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"Fraud","environment":"production"}'

3. Register a model

curl -X POST $BATMAN/models \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"project_id":"proj_...","name":"fraud-v1"}'

4. Point it at your model, then generate a key

curl -X PUT $BATMAN/models/model_.../upstream \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"url":"https://your-api.example/predict"}'

curl -X POST $BATMAN/keys \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"project_id":"proj_...","model_id":"model_...","name":"prod"}'
# -> {"api_key":"bm_live_xxxxx", ...}   (shown once)

5. Send inference through BATMAN

pip install batman-ml
from batman_ml import protect

protected = protect(api_key="bm_live_xxxxx", base_url="$BATMAN")
prediction = protected.predict(X)

Python SDK

batman-ml is a thin HTTP client (its only dependency is httpx). It does not run the detector locally — detection happens server-side.

protect()

from batman_ml import protect

protected = protect(
    api_key="bm_live_xxxxx",        # or set BATMAN_API_KEY
    base_url="https://your-batman", # or set BATMAN_BASE_URL
    raise_on_block=False,           # True -> BlockedError instead of a result
)
prediction = protected.predict(X)          # your model's output
result = protected.predict_secure(X)       # full decision + prediction

BatmanClient

from batman_ml import BatmanClient

client = BatmanClient(api_key="bm_live_xxxxx", base_url="https://your-batman")
r = client.predict(X)
print(r.action, r.threat_type, r.prediction, r.request_id)
# analyze without returning a prediction:
client.analyze(X)

Exceptions

All derive from BatmanError:

ExceptionWhen
AuthenticationErrormissing / invalid / revoked key (401)
AuthorizationErrornot permitted for the resource (403)
BlockedErrorblocked by policy (carries .decision)
RateLimitedErrorthrottled (carries .retry_after)
ValidationErrorbad payload (400/422)
UpstreamErroryour protected model failed (502/504)
ConnectionError / TimeoutErrorcould not reach BATMAN
The API key is sent only in the x-api-key header and is never logged, printed, or included in exceptions.

API integration (REST)

Prefer to call BATMAN directly? The data plane is one endpoint.

curl -X POST $BATMAN/v1/predict \
  -H "x-api-key: bm_live_xxxxx" \
  -H "Content-Type: application/json" \
  -d '{"inputs": [[/* feature vector */]], "session_id": "client-42"}'

Response:

{
  "action": "LOG",
  "threat_type": "NONE",
  "threat_level": "LOW",
  "prediction": [0],
  "request_id": "req_...",
  "latency_ms": 12.3
}
FieldMeaning
actionALLOW · LOG · RATE_LIMIT · BLOCK · ESCALATE
threat_typeNONE · API_ABUSE · MODEL_EXTRACTION · ANOMALOUS_INPUT · INVALID_REQUEST
predictionyour model's output (present when allowed)
request_idtraceable in the dashboard

A BLOCK in enforce mode returns HTTP 403; a rate-limited request returns 200 with a note or HTTP 429. Provide a stable session_id per client so behavioral analysis works across requests.

Protecting an existing ML API

BATMAN can protect a model you have already deployed — no retraining, no model change. Configure the upstream once per model: 

PUT /models/{model_id}/upstream
{
  "url": "https://your-api.example/predict",
  "method": "POST",
  "predict_path": "/predict",
  "request_format": "instances",     // "instances" | "raw"
  "response_format": "predictions",  // "predictions" | "raw"
  "auth_type": "bearer",             // "none" | "bearer" | "header"
  "auth_secret": "your-upstream-token",
  "auth_header_name": "X-API-Key",   // when auth_type = "header"
  "timeout_s": 15.0
}

Traffic then flows: Client → BATMAN → Security engine → your ML API → your model.

Upstream credentials are encrypted at rest (Fernet) and are never returned by any endpoint or written to logs. BATMAN does not attempt to understand arbitrary API schemas — declare the request/response format explicitly.

Projects & models

The resource hierarchy is User → Projects → Models → API Keys. A project carries an environment label (development, staging, production) surfaced in the dashboard. Every resource is tenant-scoped: you can only see and act on your own.

EndpointPurpose
POST /projectscreate a project
GET /projectslist your projects
POST /modelsregister a model under a project
GET /models?project_id=list models

API keys

Keys are issued by BATMAN and prefixed bm_live_. They authenticate the data plane and bind a client to one project + model.

EndpointPurpose
POST /keyscreate a key — the raw secret is returned once
GET /keyslist key metadata (never the secret)
DELETE /keys/{key_id}revoke a key
Copy a new key immediately — it is shown only at creation. Only a salted hash is stored; the raw key cannot be recovered. If lost, revoke it and create a new one.

Threat detection

Detection combines three complementary signals:

  • Deterministic rules — malformed input, NaN/Inf, oversized payloads, hard rate-limit violations. Always active.
  • Isolation Forest — an anomaly detector calibrated on your service's own normal traffic.
  • Extraction detector — scores probing/extraction behavior from request rate, query diversity, and systematic input variation across a session.

Behavioral detection needs a few requests of session history before a pattern is unambiguous, so the first requests of a new session are not blocked on the anomaly signal alone (deterministic rules still apply). This is intentional: BATMAN detects behavior across requests.

Policies

The policy engine maps threat evidence to an action. Higher severity → stronger action; deterministic high-severity rules take precedence over ML scores.

LevelAction
LOWLOG
MEDIUMRATE_LIMIT
HIGHBLOCK
UNCERTAINESCALATE

In monitor mode, blocking actions are downgraded to LOG so you can observe without enforcing. In enforce mode, policy is applied.

Telemetry

Every request produces a structured, request-id-traceable telemetry record: timestamp, project, model, session, anomaly & extraction scores, threat type, action, latency, and reason. Read it via:

EndpointPurpose
GET /v1/metricstenant-scoped summary (totals, actions, threat categories, latency)
GET /v1/threatsrecent threats for your projects
GET /v1/threats/{request_id}full detail for one incident

Analyst feedback (POST /v1/feedback) is stored separately from immutable telemetry and is used for future evaluation — never for automatic retraining.

Dashboard

The web console (auth-gated) shows only real data from your account: overview KPIs, a searchable threat log, per-incident forensic detail (evidence, scores, investigation, policy decision), plus project / model / key management. Environments are labelled DEV / STAGING / PROD, and controlled security tests are labelled CONTROLLED TEST — simulated traffic is never presented as production traffic.

Security considerations

  • API keys: cryptographically random, salted-hash storage, constant-time verification, revocable.
  • Passwords: PBKDF2-HMAC-SHA256 with per-password salt.
  • Tenant isolation: every read/write is scoped to the owning user; no cross-project access.
  • Upstream credentials: encrypted at rest (Fernet); never logged or returned.
  • Transport: use HTTPS in production. Rate limiting and request-size limits are enforced.
  • The LLM is advisory; the policy engine is authoritative.

Data handling

BATMAN stores the minimum needed for security analysis: behavioral features and decisions, not raw inference payloads by default. Model predictions are returned to the caller and not persisted. Telemetry is immutable; analyst feedback is stored separately. Configure retention according to your policy; avoid sending sensitive raw inputs unless required.

Limitations

BATMAN reduces risk; it does not eliminate it. It does not:

  • protect against every cyberattack;
  • guarantee perfect detection or zero false positives;
  • replace a WAF, SIEM, IAM, or infrastructure security;
  • guarantee detection of every adversarial example.

Detection thresholds must be calibrated against your model's own traffic distribution.

Troubleshooting

401 unauthorized

The API key is missing, malformed (must start with bm_live_), or revoked. Data-plane calls use the x-api-key header; control-plane calls use Authorization: Bearer.

403 blocked

BATMAN blocked the request by policy. Inspect the returned decision (or BlockedError.decision) for the threat type and evidence.

429 rate limited

You exceeded the per-key/session limit. Back off using Retry-After / RateLimitedError.retry_after.

502 upstream error

Your protected model API failed or was unreachable. Check the upstream URL, auth, and timeout in the model's upstream config.

Legitimate traffic is being flagged

The anomaly detector must be calibrated on your normal traffic distribution. Run in monitor mode first and tune thresholds before enforcing.
